## Defeitos reproduzidos

### F1 — Consistência do ledger pode ser quebrada por OPENING retroativa

Prioridade alta antes de main. Requisitos §5.9 e §6.2; afeta a garantia de schema e
reconciliação, sem demonstrar exploração por endpoint público.

Código: [finance_ledger_consistent](../../src/adapters/persistence/migrations/Migration202610140001.ts),
ramo wallet_version = 1 nas linhas 229–242. Regressão:
[ledger-invariants.test.ts](../../tests/persistence/ledger-invariants.test.ts).

1. Criar wallet com zero; não há OPENING nem ledger.
2. Aplicar WIN 10.00: saldo 10.00, versão 2, ledger 0.00 → 10.00.
3. Em outra transação SQL, inserir OPENING 5.00 e ledger versão 1, 0.00 → 5.00.
   Nenhuma atualização de wallet, nenhum trigger desabilitado.
4. Esperado: commit rejeitado com SQLSTATE 23514 e rollback completo.
5. Observado: commit aceito, wallet **10.00**, soma do ledger **15.00**.

O trigger confere o predecessor da linha nova e o head, mas não o sucessor já
persistido. Uma abertura zero deixa a versão 1 disponível. Correção sugerida:
proibir inserção retroativa incompatível ou validar ambos os lados da cadeia.
Preservar compatibilidade com inserções legítimas na mesma transação. Para bancos
já migrados, usar migration nova e auditar divergências existentes, sem reescrever
ou reparar silenciosamente o ledger. A correção ainda não foi implementada.

Dois controles SQL novos passaram: ROLLBACK parcial e REFUND de WIN foram rejeitados
com aritmética coerente em todos os demais campos. Isso isola as regras de valor
integral/tipo de referência, que testes anteriores misturavam com outras violações.

### F2 — Erros de parser são respondidos como falha interna

Prioridade média; requisito §9, distinção consistente entre entrada inválida e erro
de infraestrutura. Código:
[financial-error.filter.ts](../../src/adapters/http/financial-error.filter.ts),
linhas 31–48 e fallback 75. Regressões:
[http-input.test.ts](../../tests/app/http-input.test.ts).

- JSON de aproximadamente 110 KB: esperado 413; observado 500/INTERNAL_ERROR.
- application/json com charset=koi8-r: esperado 415; observado 500/INTERNAL_ERROR.

O filtro reconhece HttpException, mas os erros reais de body-parser/raw-body não
são instâncias dessa classe. Ambos os testes confirmam zero chamadas financeiras;
ambos os casos foram reproduzidos também na imagem de produção. Não houve efeito
monetário. Corrigir o mapeamento dos erros conhecidos do parser, preservando códigos
4xx e respostas sem payload/stack. Não confiar indiscriminadamente em qualquer
objeto com statusCode, para não mascarar erros internos.

### F3 — Métrica por status omite FAILED

Prioridade baixa; requisito §12. Código:
[operations.ts](../../src/adapters/observability/operations.ts), linhas 89–98, e
[telemetry.ts](../../src/adapters/observability/telemetry.ts), linhas 20–25.
Regressão: [observability.test.ts](../../tests/messaging/transaction-status-metrics.test.ts).

Uma transação FAILED/INFRASTRUCTURE_PERMANENT foi persistida legitimamente em banco
descartável. O scrape real mostrou zero nos quatro outros estados e nenhuma série
FAILED, embora houvesse uma transação nesse estado. Incluir o estado suportado no
gauge e revisar a lista compartilhada de estados. Os fluxos públicos atuais não
produzem FAILED: fazem rollback/retry/DLQ, conforme documentado. O impacto comprovado
é a omissão da métrica de um estado suportado; não há perda financeira demonstrada.

### Resultados dos probes com processos de produção

Script reproduzível: [runtime-outage.ts](../../tests/audit/runtime-outage.ts).
Usa somente serviços da stack T11, banco de negócio inicialmente vazio e cleanup de
pausas em finally. Falha abrupta do próprio script requer conferir docker compose ps.

- SQS pausado mantendo seu estado: readiness 503, liveness 200. BET 25.00 sobre
  abertura 100.00 confirmou por HTTP com saldo 75.00; dois eventos ficaram pendentes.
  Foi observado attempts>0 persistido. Após retomar SQS, publisher drenou a outbox.
- PostgreSQL pausado: readiness 503, liveness 200. WIN 10.00 foi recebido pelo
  consumidor enquanto o banco estava indisponível. Após retomar, saldo 85.00.
  O teste não exige timeout/retry PostgreSQL: a primeira consulta pode aguardar a
  retomada. Não equivale a desligamento do banco ou partição prolongada.
- Outra entrega do mesmo WIN contornou deduplicação FIFO; a métrica de replay do
  consumidor confirmou processamento da duplicata. Uma inbox, dois recibos e três
  lançamentos, saldo 85.00; replay do BET continuou com saldo original75.00.
- Todos os seis IDs da outbox foram recebidos na fila de eventos, sem ID faltante;
  DLQ vazia. Reconciliação consistente. PIDs e StartedAt dos quatro containers
  de aplicação permaneceram iguais: recuperação sem reiniciar API/workers.
- API, consumidor, publisher e referências responderam 200 em live/ready/metrics
  após os probes. O total de dois cenários não é somado aos 420 testes Bun.

## Roteiro exato para reproduzir localmente

Não é necessário que o usuário substitua uma execução obrigatória ausente: todas as
suítes locais e os contraexemplos foram executados. Este roteiro permite conferir os
resultados e, após as correções, exigir que as regressões fiquem verdes.

Pré-requisitos: Bun 1.4.3, Git, Docker/Compose/Buildx e daemon ativo. No macOS, o
[runbook da stack](../runbooks/backend.md) explica Colima. Execute na raiz do checkout.
O nome abaixo deve estar livre; não o use se já contiver dados que deseja preservar.

```sh
git switch codex/t11-readme-audit
bun install --frozen-lockfile
export DOCKER_CONTEXT=colima-backend-challenge
export COMPOSE_PROJECT_NAME=backend-challenge-t11-manual
export PORT=13011
export DB_PORT=15441
export AUDIT_APP_URL=http://127.0.0.1:13011
docker compose ps -a
docker volume ls --filter label=com.docker.compose.project=$COMPOSE_PROJECT_NAME
bun run doctor
bun run check
bun run stack:up
bun run stack:migrate
bun run stack:migrate
bun run stack:persistence
bun run stack:messaging
bun run stack:distributed
bun run stack:smoke
docker compose run --rm --build --no-deps distributed bun test tests/audit --timeout 30000
```

No Docker Desktop/Linux, omita o export de DOCKER_CONTEXT ou use o contexto do seu
daemon. Portas 13011/15441/4566 devem estar livres. Os comandos são executados
individualmente: na entrega auditada, **o último deve falhar com dois passes e quatro
falhas**. Isso comprova os defeitos, não uma instalação malfeita. Para executar
somente uma regressão, troque tests/audit pelo arquivo correspondente F1/F2/F3.
Bancos/filas de fixture são exclusivos e removidos ao final.

Para os dois probes operacionais, a wallet de negócio deve continuar vazia; execute
antes de exemplos manuais ou use outra stack exclusiva:

```sh
bun run stack:workers
bun tests/audit/runtime-outage.ts
```

Esperado: dois registros JSON de sucesso, saldo 85.00, seis eventos recebidos,
uma inbox, dois recibos, três lançamentos e mesmos processos de produção. SQS tem
retry observado; PostgreSQL tem receive durante pausa e conclusão após retomada,
sem afirmação de retry. Se interromper o próprio script, retome qualquer serviço
que ficou pausado antes de repetir/encerrar:

```sh
docker compose ps -a
docker compose unpause postgres localstack
```

Somente quando COMPOSE_PROJECT_NAME ainda identificar a stack descartável escolhida,
remova seus recursos:

```sh
docker compose --profile workers down --volumes
```

Esse encerramento apaga dados da revisão; não use o nome da stack habitual.
O script de outage exige nome backend-challenge-t11-* justamente para recusar a
stack padrão. Não usa prune, não encerra SQL Server e não desliga Colima.
